# A000018 — positive integers ≤ 2ⁿ of the form x² + 16y²

## Vision
`a(n)` counts the distinct positive integers up to `2ⁿ` expressible as `x²+16y²` for non-negative
integers `x, y`. The naive framing ("which numbers qualify?") hides the actual computational
content: different `(x,y)` pairs can produce the identical value, so naively counting `(x,y)` pairs
overcounts, and the page's central claim is that the real work in this sequence is finding and
merging those collisions — not filling out a grid. A secondary, honestly-scoped claim: every number
counted here is automatically a sum of two squares (`x²+16y² = x²+(4y)²`), a real but merely
NECESSARY condition, not a full characterization.

## Terms
MUST/MUST NOT/SHALL/SHOULD/SHOULD NOT/MAY as in RFC 2119. Uses two catalogued devices, one new to
the catalog and one reused unchanged:
[device::RepresentationGrid](../../_terms.md#devicerepresentationgrid),
[device::LogGrowthChart](../../_terms.md#deviceloggrowthchart).

## Scope
**In scope:** `memory-bank/visualizations/A000018/viz.html` — the current, only page for this
sequence (no kept drafts) — and the `solution.mjs`/`proof.mjs` pair. This page is also the shared
explanation for A000021 and A000024 (the same construction, `x²+12y²` and `x²+10y²`), which link
here rather than each carrying their own picture.

**Out of scope:** a full characterization of which integers/primes ARE representable by `x²+16y²`
(this would require quartic/biquadratic reciprocity, well beyond what the page draws or checks);
A000021's and A000024's own write-ups, which state plainly they borrow this page.

## Architecture

### Overview (prose)
`memory-bank/visualizations/A000018/viz.html` runs Problem (the first ten counts, no visible rule)
→ (1: a 5×5 grid of `x²+16y²` for `x,y=0..4`, via
[device::RepresentationGrid](../../_terms.md#devicerepresentationgrid), with the real collision at
value `16` — cells `(4,0)` and `(0,1)` — linked, showing why counting grid cells would overcount) →
(2: the hidden necessary condition, `x²+16y²=x²+(4y)²`, worked on `17=1²+4²`, stated honestly as
necessary not sufficient) → Solution (the growth chart from `n=0` to `n=20`, via
[device::LogGrowthChart](../../_terms.md#deviceloggrowthchart), reused unchanged from A000001 and
A100001, with a verified-match badge citing `proof.mjs`'s actual run).

### Code
`sequences/A000018/solution.mjs` sieves every value `x²+16y² ≤ bound` into a flat byte array
indexed by the value itself and counts first-time marks — a `Set` of matched values was tried first
and hits V8's own maximum-Set-size limit around 2²⁴ entries well before memory runs out, which is
why the sieve is a byte array rather than a set.
`sequences/A000018/proof.mjs` does not reuse that sieve: for every candidate value from 1 to the
bound, it independently tests membership by looping over `y` and checking whether `v−16y²` is a
perfect square — a per-candidate test rather than a per-`(x,y)`-pair generator, catching both a
spurious mark and a missed one in the same pass — before comparing final counts to OEIS's published
terms.
