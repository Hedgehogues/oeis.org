# A000002 — Kolakoski sequence

## Vision
`a(n)` is the length of the `n`-th maximal run of a sequence built from only `1`s and `2`s, with
`a(1) = 1`. The naive question ("what's the next 1 or 2?") gives no handle on why any particular
choice is forced. The page's central claim: the sequence is a FIXED POINT of run-length encoding —
reading off the lengths of its own runs, in order, reproduces the sequence itself — and that one
property is enough to determine every term, because at each step the length of the run being
written is a term the sequence already wrote earlier in itself.

## Terms
MUST/MUST NOT/SHALL/SHOULD/SHOULD NOT/MAY as in RFC 2119. Uses three catalogued devices
(`../../_terms.md`), two new to the catalog and one reused unchanged:
[device::RunLengthEncoding](../../_terms.md#devicerunlengthencoding),
[device::FixedPointOverlay](../../_terms.md#devicefixedpointoverlay),
[device::MiniRecap](../../_terms.md#deviceminirecap).

## Scope
**In scope:** `memory-bank/visualizations/A000002/viz.html` — the current, only page for this
sequence (no kept drafts) — and the `solution.mjs` / `proof.mjs` pair that computes and checks the
sequence itself.

**Out of scope:** the devices' own quality requirements (`../../specs/approaches.md`,
`../../specs/visualizations.md`); the sequence's unsolved density conjecture (density of `1`s = 1/2)
beyond the honest empirical badge the Solution section shows — the page does not claim to resolve
it.

## Architecture

### Overview (prose)
`memory-bank/visualizations/A000002/viz.html` runs Problem (a strip of terms, no visible rule) →
(1: what a run is, via [device::RunLengthEncoding](../../_terms.md#devicerunlengthencoding), a
worked example on the first 9 terms) → (2: the punchline, via
[device::FixedPointOverlay](../../_terms.md#devicefixedpointoverlay), the 6 run lengths from step 1
checked column-by-column against `a(1)..a(6)`) → (3: the construction rule, via
[device::MiniRecap](../../_terms.md#deviceminirecap) reused exactly as catalogued — each of 4 frames
reuses a shrunk copy of the growing prefix with the term being read highlighted, and the newly
appended run highlighted in a second, distinct colour) → Solution (90 generated terms, a
verified-match badge citing `proof.mjs`'s actual run, and an empirical density stat captioned as
evidence toward — not proof of — the sequence's own open density conjecture).

### Code
`sequences/A000002/solution.mjs` computes `a(n)` by exactly the procedure the page draws: `a(1)=1`
forces run 1 to length 1; run 2's alternated colour fixes term 2 (hence `a(2)=2`) independently of
its own length; from there a read pointer trailing the write frontier supplies each next run's
length from a term the sequence already wrote. `sequences/A000002/proof.mjs` does not reuse that
bootstrap: it re-scans the output with a plain left-to-right run-length pass sharing no code with
the generator, drops the possibly-truncated final run, and checks that every remaining run's length
equals the corresponding term of the sequence itself — the definitional property, checked from
scratch — then separately checks soundness (every term in `{1,2}`, `a(1)=1`) and agreement with
OEIS's published terms.
